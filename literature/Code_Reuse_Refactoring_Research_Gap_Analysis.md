# Code Reuse / Refactoring with AI — обзор близких работ и исследовательские идеи

**Проект №10**  
**Авторы проекта:** Evgenii Lialin и Roman Vikhman  
**Дата обзора:** 23 октября 2026 года  
**Статус:** предварительный анализ литературы, не доказательство научной новизны.

## 1. Основная идея проекта

Исследовать, **используют ли большие языковые модели (LLM) уже существующие функции проекта при рефакторинге**, вместо того чтобы дублировать их реализацию, и **как способ поиска контекста репозитория влияет на этот результат**.

Возможный исследовательский вопрос:

> **Does repository-aware retrieval improve existing code reuse during LLM-based refactoring?**

По-русски: «Повышает ли поиск с учётом структуры репозитория вероятность повторного использования существующего кода при рефакторинге с помощью LLM?»

Важно разделить **поиск подходящей функции**, **фактическое её использование** и **сохранение корректности программы**. Эти три задачи не эквивалентны.

## 2. Ближайшие опубликованные исследования

### 2.1 RepoExec — On the Impacts of Contexts on Repository-Level Code Generation

- **Авторы:** Nam Le Hai, Dung Manh Nguyen, Nghi D. Q. Bui.
- **Публикация:** Findings of NAACL 2025 (не основной трек).
- **Статья:** https://aclanthology.org/2025.findings-naacl.82/
- **PDF:** https://aclanthology.org/2025.findings-naacl.82.pdf
- **Код и данные:** https://github.com/FSoft-AI4Code/RepoExec

**Что уже сделано.** Представлен benchmark RepoExec для генерации кода на уровне репозитория. Авторы исследовали 18 моделей, функциональную корректность, использование зависимостей и влияние контекста. Предложена метрика **Dependency Invocation Rate (DIR)**. Обнаружено, что модель может генерировать правильный код, но повторно реализовывать уже существующие зависимости; instruction tuning повышает использование зависимостей.

**Пересечение с нашим проектом:** очень высокое в части **code reuse и измерения вызовов существующих функций**.

**Возможное отличие:** RepoExec прежде всего посвящён **генерации** кода, тогда как мы можем исследовать **рефакторинг уже существующего кода** и целенаправленное устранение дублирования.

**Что проверить в полном тексте:** как определена DIR, как строятся задачи, какой контекст доступен модели, не исследовались ли уже именно преобразования по типу Extract Method / Replace Duplicate Code.

### 2.2 MANTRA — Enhancing Automated Method-Level Refactoring with Contextual RAG and Multi-Agent LLM Collaboration

- **Авторы:** Yisen Xu и соавторы.
- **Год:** 2025.
- **Источник:** arXiv; соответствие требованиям Марины по конференциям необходимо проверять отдельно.
- **Статья:** https://arxiv.org/abs/2503.14340

**Что уже сделано.** MANTRA сочетает контекстный RAG, совместную работу нескольких LLM-агентов и обратную связь для рефакторинга методов. Авторы оценили **703 случая чистого рефакторинга из 10 Java-проектов**. По аннотации, **82,8%** результатов MANTRA компилировались и проходили тесты против **8,7%** у сравниваемой базовой модели; показатели относятся к конкретному benchmark и baseline.

**Пересечение:** очень высокое по **LLM + RAG + автоматический рефакторинг**.

**Возможное отличие:** измерять не общий успех рефакторинга, а **нахождение и фактическое повторное использование уже существующих функций**.

**Что проверить:** виды рефакторинга, retrieval ablations, метрики reuse и случаи, когда система создаёт новую функцию вместо вызова имеющейся.

### 2.3 RepoAI — Automated Code Refactoring Through Multi-Agent LLM Orchestration and Retrieval-Augmented Generation

- **Авторы:** Nacha Chondamrongkul и соавторы.
- **Издание:** *Science of Computer Programming*, 2026, статья 103477.
- **DOI:** 10.1016/j.scico.2026.103477
- **Статья:** https://www.sciencedirect.com/science/article/pii/S0167642326000432

**Что уже сделано.** Открытая многоагентная система рефакторинга на уровне репозитория с RAG и валидацией. Авторы сравнивают стратегии retrieval и варианты pipeline, проводят **1 404 попытки выполнения задач** на основе RefactorBench и тестируют семь моделей четырёх семейств. Полная система статистически превосходит прямую генерацию в их оценке, однако в статье отмечен небольшой размер эффекта и потолочный эффект benchmark.

**Пересечение:** особенно высокое с идеей **сравнить retrieval-подходы в рефакторинге**.

**Возможное отличие:** отдельная причинная оценка **retrieval success → reuse success → functional correctness**, а не агрегированная оценка качества рефакторинга.

**Что проверить:** действительно ли авторы уже измеряют вызов конкретной существующей функции; сравниваются ли BM25 и embeddings; как контролируется длина контекста.

### 2.4 CodeTaste — Can LLMs Generate Human-Level Code Refactorings?

- **Авторы:** Alex Thillen, Niels Mündler, Veselin Raychev, Martin Vechev.
- **Конференция:** ICML 2026.
- **Статья:** https://proceedings.mlr.press/v306/thillen26a.html

**Что уже сделано.** Benchmark реальных многофайловых рефакторингов. Различаются две задачи: **выполнить подробно заданный рефакторинг** и **самостоятельно обнаружить полезный рефакторинг, выбранный разработчиками**. Проверка сочетает тесты и статические проверки желаемых/нежелательных паттернов. Агенты заметно хуже справляются с самостоятельным выбором изменений, чем с выполнением конкретной инструкции.

**Пересечение:** оценка **реалистичных рефакторингов** и выявление возможностей улучшения кода.

**Возможное отличие:** специально изучить **обнаружение уже существующего подходящего helper-кода и его повторное использование**.

**Что проверить:** можно ли использовать benchmark или методику статических проверок для собственных задач.

### 2.5 CoRet — Improved Retriever for Code Editing

- **Авторы:** Fabio James Fehr и соавторы.
- **Конференция:** ACL 2025, Short Papers.
- **Статья:** https://aclanthology.org/2025.acl-short.62/
- **PDF:** https://aclanthology.org/2025.acl-short.62.pdf

**Что уже сделано.** Dense retriever для задач изменения кода с учётом семантики, структуры репозитория и графа вызовов. На задачах локализации ошибок авторы сообщают об увеличении retrieval recall минимум на **15 процентных пунктов** относительно сравниваемых систем.

**Пересечение:** методика поиска **релевантного кода** для последующего редактирования.

**Возможное отличие:** проверить, улучшение retrieval recall приводит ли к **фактическому повторному использованию функции** в рефакторинге.

**Ограничение:** высокий recall поиска сам по себе не гарантирует корректного рефакторинга.

## 4. Рекомендуемая постановка исследования

**Рабочее название:** *Repository-Aware Retrieval for Existing Code Reuse in LLM-Based Refactoring*.

**Основной вопрос:** повышает ли retrieval вероятность того, что LLM при рефакторинге заменит дублирующуюся логику вызовом уже существующей функции, не нарушив поведение программы?

**Подвопросы:**

1. Как часто подходящая функция вообще находится поисковой системой?
2. Как часто LLM вызывает найденную функцию, а не пишет аналогичный код заново?
3. Насколько часто такие изменения сохраняют корректность?
4. Как влияет способ retrieval: без поиска, BM25, dense embeddings, agentic search, oracle?
5. Влияет ли явная инструкция «используй существующие функции» на результаты?
6. Что происходит, если правильная функция найдена, но модель всё равно не использует её?

## 5. Предлагаемый дизайн эксперимента

### Условия

- **C0 — No retrieval:** только целевой код и минимальные необходимые инструкции.
- **C1 — BM25:** дополнительно найденные лексическим поиском функции.
- **C2 — Dense retrieval:** функции, найденные embeddings.
- **C3 — Agentic retrieval:** модель может итеративно искать код в репозитории.
- **C4 — Oracle:** явно предоставлена заранее известная подходящая функция.

**Контроль:** одинаковые модели, версии, температурные настройки, тестовые задачи, бюджет токенов (насколько возможно), лимиты времени и критерии успеха. Для агентного условия отдельно фиксировать число вызовов инструментов.

### Метрики

1. **Retrieval Recall@k / MRR:** насколько часто найден нужный helper.
2. **Reuse Rate / Dependency Invocation Rate:** вызван ли существующий helper в итоговом коде.
3. **Functional Correctness:** проходят ли тесты, включая дополнительные проверки поведения.
4. **Valid Refactoring Rate:** выполнено ли структурное улучшение без изменения поведения.
5. **Duplication Reduction:** действительно ли уменьшилось дублирование.
6. **Cost / Latency:** токены, денежная стоимость, время.

**Нюанс оценки:** вызов заранее назначенного helper — полезная, но неполная метрика. Модель может использовать другой эквивалентный helper; часть случаев нужно вручную разметить. Прохождение тестов также не является математическим доказательством эквивалентности поведения.

### Данные

- **Синтетические задачи:** удобно задавать известный helper и автоматически проверять ответ, но возможны искусственные подсказки и смещение распределения.
- **Реальные изменения GitHub:** реалистичнее, но сложнее получить однозначный правильный ответ.
- **Рекомендация:** сочетать оба типа и публиковать результаты отдельно.
- **Предотвращение утечки:** разделять проекты по репозиториям, учитывать возможность присутствия исходного кода в обучающих данных LLM и не включать эталонный helper в baseline-контекст случайно.

### Первый пилот

- 20–30 вручную проверенных задач;
- 2 LLM;
- сначала C0, C1 и C4;
- два типа инструкций: нейтральная и явная ориентация на reuse;
- повторить прогоны при недетерминированных настройках;
- зафиксировать все prompts, версии моделей, результаты тестов и git diffs.

После пилота решить, нужны ли C2 и C3, и провести анализ ошибок до масштабирования.

## 6. Как интерпретировать возможные результаты

- **Высокий recall, низкий reuse:** проблема не только в поиске, но и в выборе моделью стратегии изменения кода.
- **Высокий reuse, низкая корректность:** модель вызывает существующий helper неправильно.
- **C4 значительно лучше C1/C2:** bottleneck — retrieval.
- **C4 тоже слабый:** bottleneck — способность модели применить найденную функцию.
- **Agentic search лучше, но дороже:** нужен анализ компромисса качество/стоимость.
- **Нет различий:** тоже содержательный результат, если эксперимент достаточно мощный и условия сопоставимы.

## 9. Ключевой вывод

Тема №10 остаётся сильной, но общие идеи «LLM + RAG + refactoring» и «поиск существующих зависимостей» уже исследованы. Наиболее интересная **проверяемая гипотеза** для проекта Евгения и Романа — изучить, **на каком именно этапе теряется повторное использование существующего кода: при поиске, принятии решения моделью или при внесении корректного изменения**. Эта формулировка пока **не заявлена как доказанная научная новизна**.
